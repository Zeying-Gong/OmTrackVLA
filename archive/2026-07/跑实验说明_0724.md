# 0724 实验说明：三种输入模式的行人跟随导航

## 1. 最终要解决的问题

系统的原始目标不是让机器人在陌生场景中寻找某个目标，而是：

> 第一帧机器人已经看到目标行人，得到目标图像或目标框；随后行人移动，机器人持续跟随。目标可能因为遮挡、转弯或离开视野而暂时不可见，系统需要进行预测、重新捕获和身份确认。

系统需要支持三种目标指定输入模式：

1. **纯视觉模式**：输入首帧目标 RGB/crop，使用检测、分割、ReID 和跟踪确定目标位置并持续跟随。
2. **纯坐标模式**：输入以机器人为原点的目标相对方位和距离（UWB 或人工指定），根据相对坐标跟随目标。
3. **混合模式**：同时输入目标图像和目标相对坐标。坐标用于缩小搜索区域和提供遮挡期间的粗定位，视觉用于确认目标身份和精确定位。

Habitat 的 ImageNav 只能作为图像条件导航接口的早期验证。它常用的是“目标位置看到的场景图像”，并不等价于“给定某个行人的 crop 后持续跟踪该行人”。最终需要额外的目标实例数据：目标 crop、实例 ID、目标位置、可见性、不同视角以及遮挡/重现片段。

## 2. 统一算法表示

推荐把三种输入统一转换成当前视野中的目标状态，而不是让导航网络直接处理尺寸任意的目标 crop：

```text
视觉 / 坐标 / 混合目标
          ↓
目标检测、分割、ReID、坐标投影和跟踪
          ↓
Pixel Goal + range + target velocity
          + visible + confidence + modality mask
          ↓
局部避障和跟随控制
          ↓
连续线速度、角速度
```

Pixel Goal 建议使用行人 bbox 的底部中心或分割得到的脚点，不建议直接使用 bbox 中心。仅有像素 `(u, v)` 不够，还应保留深度/距离、可见性、跟踪置信度和目标运动估计。

目标 crop 尺寸不一致不是接口问题：用保持比例的 resize + letterbox 送入 ReID/目标编码器。crop 主要用于首帧身份初始化和丢失后的重新识别；导航模块主要接收当前 RGB-D、目标像素热图和目标状态。

### 三种模式的适配

- **纯视觉**：首帧 crop → 检测/ReID 初始化 → 当前帧 bbox/mask → 脚点 Pixel Goal。
- **纯坐标**：相对坐标 → 相机投影；目标在视野外时使用图像边界方向或 rotate-first 状态。
- **混合**：相对坐标产生候选 ROI，视觉/ReID 确认是否为目标并给出精确脚点；视觉暂时丢失时由坐标提供粗定位。

PixelNav 是局部能力。目标在另一个房间、长时间被遮挡或完全离开视野时，还需要记忆、重定位、子目标或有限范围搜索，不能只依赖单帧 Pixel Goal。

## 3. 推荐系统结构

### 3.1 目标感知前端

建议使用成熟模块组合，而不是首先训练一个端到端大模型：

- YOLO/RT-DETR：行人检测；
- SAM 或实例分割：获得更稳定的目标脚点；
- ByteTrack、BoT-SORT 或 StrongSORT：短时跟踪；
- ReID embedding：遮挡后恢复并避免身份切换；
- RGB-D 或深度模型：估计目标距离和可行走方向。

状态机应包含：`TRACKING`、`SHORT_OCCLUSION`、`REACQUIRE`、`SEARCH`、`FAIL`。

目标暂时不可见时按以下顺序处理：

1. 短时遮挡：用目标速度和机器人位姿预测目标位置。
2. 目标从视野边缘离开：原地转向或小范围移动，优先使目标重新进入视野。
3. 重新检测到行人：用 ReID 与历史特征匹配，避免跟错人。
4. 长时间丢失：结合 UWB/最后运动方向做有限范围搜索，并设置超时。

### 3.2 控制/导航后端

先实现一个几何视觉伺服基线：

```text
角速度 = k_angle * (target_u - image_center_u)
线速度 = k_distance * (target_range - desired_follow_range)
```

需加入角度门控：目标偏离较大时先转向，降低线速度，避免高速撞墙或冲出视野。

NavDP 作为局部轨迹和避障先验更合适，而不是负责目标识别。它可以接收目标 Pixel Goal、距离、可见性等统一表示，负责在复杂室内环境中输出局部连续轨迹，再由控制器转换为 Habitat 的 `VelocityAction`。

最终建议：

```text
检测/跟踪前端 + 几何控制器（第一版基线）
检测/跟踪前端 + NavDP（复杂障碍环境）
NavDP 初始化 + 统一数据集模仿学习 + RL 微调（最终版本）
```

不建议现在完全从头训练端到端策略：数据需求大，目标身份、深度、坐标转换和控制错误难以区分。也不建议把独立 PointNav 和 ImageNav 数据简单拼接；三种模式应从同一个目标和 oracle trajectory 派生，确保轨迹标签一致。

## 4. 训练路线

### 阶段 A：接口和跟踪闭环

1. 在 Habitat 中生成首帧可见的行人/目标实例序列。
2. 验证检测框、分割脚点、深度、相对坐标和 Pixel Goal 的坐标系。
3. 使用几何控制器跑通正常跟随、转弯、速度变化和短时遮挡。
4. 分别测试纯视觉、纯坐标、混合模式。

### 阶段 B：统一模仿学习数据

每个 episode 保存对齐数据：

```text
RGB-D history
point goal / relative coordinate
target crop 和实例 ID
Pixel Goal / bbox / mask / depth
visible、confidence、modality mask
target velocity
oracle future local trajectory
碰撞、转向和恢复标签
```

从同一个 episode 生成 Point-only、Image-only 和 Hybrid 样本，训练连续动作策略。训练时使用 oracle path 产生局部轨迹标签，并加入遮挡、检测噪声、目标运动和控制扰动。

推荐顺序为：Behavior Cloning → 受扰动数据/DAgger → 动态行人数据微调。

### 阶段 C：交互式强化学习

只有在跟踪和导航闭环已经稳定后再做 RL。行人必须在环境中在线移动，策略才能获得碰撞、距离、身份保持和跟随稳定性反馈。只有预录制行人视频的数据集属于离线数据，不能直接当作标准在线 RL 环境。

奖励可包含：目标距离误差、目标像素水平误差、跟丢惩罚、身份切换惩罚、碰撞惩罚、速度平滑和到达/持续跟随奖励。


关键接口约定：

- Habitat 世界坐标：X 向右、Y 向上、-Z 向前；
- Habitat PointGoal 的正 theta 表示目标在左侧；
- NavDP/机器人基座：x 向前、y 向左、yaw 逆时针为正；
- PointGoal 转 NavDP 平面坐标使用 `[x, y] = [rho*cos(theta), rho*sin(theta)]`，不能再对 y 取反；
- NavDP 标签是缩放后的 delta pose，推理时先除以 4，再对 delta 做累加；critic 应评分 delta 序列，而不是错误地评分累计轨迹。

曾出现的 `distance_to_goal=inf` 主要来自 Habitat 运行时重建 navmesh，导致起点和终点落在不同 island，并不一定是原始 episode 异常。HM3D 评测应使用打包的 scene navmesh：

```yaml
habitat.simulator.default_agent_navmesh: false
```

当前已验证的参考结果：开放场景 episode 20 可从约 3.434 m 降至 0.169 m，16 步成功，SPL 约 0.989。复杂 episode 6 虽然可达，但 NavDP 第一步预测方向已经偏离 oracle path，100 步后仍有约 5.272 m 距离；这说明后续需要先检查输入历史、相机姿态和轨迹预测质量，再调控制器速度，不能简单归结为坐标转换错误。

当前历史帧仍需与训练保持一致：训练使用 8 帧、每 4 帧采样一次、早期不足用零填充；适配器不能继续使用连续帧和首帧复制填充。还需要做水平相机与约 30° 下视相机的 A/B 测试。

速度环境变量：

```bash
NAVDP_MAX_LINEAR=0.4
NAVDP_MAX_ANGULAR=0.4
```

Habitat 当前物理配置约为：

```yaml
lin_vel_range: [-0.25, 0.25]  # m/s
ang_vel_range: [-30, 30]      # deg/s
time_step: 1.0
```

因此必须同时关注归一化控制器上限和 Habitat 的物理速度。目标偏离较大时应降低线速度或先旋转。

### 10 步动态 oracle 跟随

多步版本每一步重新读取目标真值、计算到动态行人的 navmesh 最短路径方向并输出连续速度。距离过远时 `approach`，进入安全距离带时 `hold`，过近时在 navmesh 上搜索增加人与机器人间距的安全撤离点后 `retreat`。

```bash
OMTRACKVLA_XVFB_DISPLAY_NUM=206 CUDA_VISIBLE_DEVICES=0 \
PYTHONPATH=/robot/robot-research-exp-0/user/gzy/OmTrackVLA/habitat-lab:/robot/robot-research-exp-0/user/gzy/OmTrackVLA \
./run_xvfb.sh \
/robot/robot-research-raw-data-0/user/gzy/temp/miniconda3/envs/tracevln_V2/bin/python -u \
oracle_modular_follow.py \
  --task stt --split train \
  --scene 16tymPtM7uS --episode-id 4 --match-index 0 \
  --steps 10 --min-distance 1.2 --max-distance 1.5 \
  --max-forward 0.25 --max-yaw 0.35 --video-fps 4 \
  --output-dir outputs/oracle_modular_follow_fast
```

10 步距离变化：`2.275 → 2.123 → 2.030 → 1.936 → 2.044 → 2.067 → 2.068 → 2.111 → 2.097 → 2.133 → 2.265 m`。行人在第 3 步后转弯并加速，机器人保持在约 2 m，全程目标可见且 `human_collision=0`。

EVT-Bench 当前 Tracking Rate 的每步 `human_following` 判定不是简单的“bbox 可见”：要求人与机器人欧氏距离不超过 `3 m`，并且目标 panoptic mask 像素数大于 `10000`、小于画面面积的 30%。最终 success 距离带为 `[1 m, 3 m]`，小于 `0.5 m` 记作人与机器人碰撞。此次 mask 面积为 `3518~5393`，所以虽然目标持续可见且距离小于 3 m，官方 `human_following` 仍为 0。后续需要讨论 `10000 px` 阈值是否适合 384×384 相机，而不能把该值直接理解为跟踪失败。
