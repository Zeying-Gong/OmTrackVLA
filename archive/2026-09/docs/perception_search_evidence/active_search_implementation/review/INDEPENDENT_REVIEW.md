# 独立 FSM 审查与 v3 修复

结论：原模块 33 项测试通过，但异步输入反例暴露三类实际缺陷。经 root 授权，在完整保存 `history/v2/` 后修复了独立实现；可安装副本现已通过 **50/50 本机 CPU 测试**。没有改 repo 主模块、冻结 runner、训练样本或模型，没有部署搜索，没有发送动作。

## 已修复问题

1. **旧许可覆盖新撤销。** v2 收到更新的 DENY/UNKNOWN 后，仍可接受在新鲜度窗口内的旧 ALLOW；同一时间戳的冲突值也可恢复搜索。v3 为全部有效许可类型保存时间戳水位，拒绝回退。相同时间戳若出现不同值，则该时间戳不可再授权，必须收到更新的合法许可。即使 RGB 缺失、policy_stop、初始化短时缺失或控制时间重复导致本步停车，仍先保存有效许可撤销。
2. **缓存帧伪造确认持续时间。** v2 使用回调 `now` 的跨度和间隔，0.002 秒拍摄的三张图可经延迟返回凑满 0.3 秒。v3 使用 RGB 采集时间计算持续跨度，同时约束采集间隔与回调间隔；新鲜度、不同帧计数、同一身份和保护优先级仍全部保留。
3. **重复帧续签目标记忆。** v2 用处理时刻刷新最后可信时间，旧图被重复处理或晚到会推迟允许搜索的记忆期限。v3 只以更晚采集的 strong 同目标帧刷新记忆时间和可信方向，被动重获也采用末帧真实采集时刻。

修复前的 9 条额外测试有 8 条失败，原始 unittest 输出保存在 `history/v2/ASYNC_RED_EVIDENCE.json`。另外一项固定种子的连续预算检查通过，未发现原命令预留算法超出声明上界。新增正向用例验证：更新许可可以恢复、相同 ALLOW 不续期、未来非法许可不污染水位、实际足够时长的延迟帧仍能确认，以及新采集强证据能正常更新记忆。

原 TTL 用例用了 `.30` 的许可覆盖已接收 `.31` 水位，这在修复后应被拒绝。该用例已改为 `.32` 的合法延迟许可，验证有效期仍缩短至 `.47`；拒绝旧许可由明确反例负责。这没有放松新鲜度或预算门槛。

## 保留的状态与预算语义

- 冷启动不搜索；任务 nonce 变更必须 reset；短时缺失不清目标或预算。
- 模糊/未知身份不会变成 TRACKING；绑定标志与 GT 不能直接授予 KNOWN_SAME。
- 预算耗尽后可以被动确认同一目标，但重获不退还 lost/search/yaw/reversal 预算。
- 非零命令仍为零平移、受限偏航，TTL 受全部输入、许可、采集时刻计算的目标记忆以及剩余预算约束。
- 同一许可的重复 ALLOW 只在原有效期内可用；相同时间戳冲突必须用更新许可解除。非法、未来或陈旧许可不抬高时间戳水位。
- `tracking_ready` 仍只是给未来 dispatcher 的状态标志，不是已发跟随动作，也没有替代执行端 watchdog。
